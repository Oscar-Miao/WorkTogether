# 从客户视角体验 MVP：可执行试用方案

入驻流程已更新：先按 [账号注册与团队入驻](../architecture/team-onboarding.md) 用两个独立账号注册；一人创建团队及首项目，从聊天内“团队与项目”生成邀请，另一人注册／登录后确认加入，再加入项目公开群。无需共用初始化维护账号。以下旧邀请开户流程保留兼容，不能代替新客户入驻。

这份方案的重点是用户能否完成协作、理解判断并得到价值。它适用于现有单工作空间、单项目、单主设备版本。下面的数字是首轮试用的建议目标，不是已经达到的产品指标。

## 1. 先体验什么

第一轮让自己扮演三个真实角色，第二轮邀请一个 3～5 人的小组做实际工作。体验过程中不要预先解释工具、CLI、worktree 或审批指纹；这些是实现机制，不能成为普通成员上手的前提。

| 角色       | 想完成的事情                                     |
| ---------- | ------------------------------------------------ |
| 项目维护者 | 创建协作环境、邀请成员、连接主设备并设置能力边界 |
| 成员小林   | 正常讨论并认领一项工作，不希望 Agent 抢做        |
| 成员小周   | 委托 Agent 帮忙，能发现已有工作，并在误判后纠正  |

维护者是人，Owner Node 是设备。只有设置设备策略的人需要理解部署和执行权限；普通成员使用群聊、提及、协作卡和资料即可。

## 2. 准备一个独立的试用环境

先构建，再用新的数据目录启动，避免把试用消息、账号和认领记录混入日常环境。下列命令在新开的 PowerShell 中执行，端口使用 3003：

```powershell
Set-Location -LiteralPath 'E:\项目实践2\demo'
pnpm build
if ($LASTEXITCODE -ne 0) { throw '构建失败，请先修复错误' }

$env:NODE_ENV = 'development'
$env:TEAM_AGENT_SERVER_DATA_DIR = '.local/pilots/customer-01/server'
$env:API_HOST = '127.0.0.1'
$env:API_PORT = '3003'
$env:WEB_ORIGIN = 'http://127.0.0.1:3003'
$env:OWNER_EMAIL = 'pilot-owner@team.local'
$pilotPassword = Read-Host '设置试用维护者密码（至少 12 位）' -AsSecureString
$env:OWNER_PASSWORD = [System.Net.NetworkCredential]::new('', $pilotPassword).Password
$env:COORDINATOR_ENABLED = 'false'
$env:TEAM_AGENT_RETENTION_ENABLED = 'false'
node --input-type=module -e "process.env.DATABASE_URL=''; await import('./apps/api/dist/main.js')"
```

访问 http://127.0.0.1:3003，手动填写上面的试用邮箱和刚设置的密码。这使用构建后的 Web 与 API 同一端口，不需要另外启动 Vite。PGlite 仅由这一进程打开。环境变量仅影响当前终端及其子进程，不需要改动 .env.local。启动命令在 Node 进程内显式清空 DATABASE_URL，确保不使用 .env.local 中可能存在的其他数据库地址；Windows PowerShell 中给环境变量赋空串可能直接删除变量，因此没有用它来隔离数据库。

同一个 customer-01 目录后续继续保留账号与历史；换成 customer-02 可创建新的试用空间。不要在另一个实例中同时打开同一个数据目录。

先使用规则观察模式测试交互和精确重复；要评估自然语言理解，再按 README 配置协调器真实模型并重启本试用 API。两轮分别记录结果，不能把规则模式表现当成语义理解质量。

## 3. 一个人模拟三个客户

分别使用 Chrome 普通窗口、Chrome 无痕窗口、Edge 无痕窗口，或三个独立浏览器配置文件。三个普通标签页会共享登录 Cookie，不能代表三个独立成员；同一浏览器的多个无痕窗口通常也共享该无痕会话。

1. 维护者登录，打开主设备侧栏中的团队成员管理，分别为两个试用邮箱生成项目邀请链接。
2. 在另外两个独立会话打开对应链接，设置小林、小周的名字和密码，再用受邀邮箱登录。
3. 小林创建“客户体验组”，使用公开加入或群邀请码把小周加入。
4. 由成员自己找到 @成员、@AI、协作卡、资料和成员侧栏，不替他们解释按钮位置。

项目邀请用于建立账号，群邀请码用于加入具体群，两个入口应分别检查是否容易理解。邀请链接无需真实邮箱服务即可接受；目前不能据此声称已实现邮件发送。

如果需要自动化多账号，Playwright 的独立 BrowserContext 可以隔离 Cookie 和存储。[官方隔离说明](https://playwright.dev/docs/browser-contexts) 支持这种测试方式。当前已有桌面和手机视口的浏览器回归；它们不能替代真实用户观察和物理手机测试。

## 4. 按客户目标走一遍

下面按顺序执行。前七项不要求真实 Pi；执行、停止和质量检查需要另外连接主设备。

| 场景         | 客户操作                                           | 应看到的结果                                  | 重点观察                           |
| ------------ | -------------------------------------------------- | --------------------------------------------- | ---------------------------------- |
| 首次进入     | 不看说明，尝试找到群并发一条消息                   | 能独立完成基本聊天                            | 5 分钟内能否上手；第一个疑问是什么 |
| 创建和加入群 | 小林建群，小周加入                                 | 群列表、成员、消息一致                        | 是否分清项目邀请与群邀请           |
| 提及同事     | 发“@小林 帮我确认这个说明”                         | 指向正确成员，不因为提及同事就启动 Agent 执行 | 客户能否理解 AI 与人的区别         |
| 人工认领     | 小林发“我来做 登录页表单校验”，再确认认领          | 协作卡显示人工负责                            | 是否必须反复填写同一需求           |
| 拦住精确重复 | 小周发“@AI 登录页表单校验”                         | 关联已认领工作，不再新开同范围执行            | 是否看得懂原因和谁在负责           |
| 纠正误判     | 在复核中补充具体差异，如客户端、验收或代码基线     | 重新判断，有明确差异时不机械拒绝              | 能否在原卡完成纠正                 |
| 资料引用     | 创建资料、引用后发送，再刷新页面                   | 引用版本明确，草稿和历史可恢复                | 是否知道本次用了哪份资料           |
| 明确委托     | 连接只读主设备后发“@AI 分析项目结构并列出风险清单” | 出现目标、真实执行进度和报告                  | 看得懂在做什么、做到了哪           |
| 停止执行     | 在确实仍在运行的任务卡点击停止                     | 先反馈请求，再展示确认结果；未确认时明确标记  | 不能立刻伪装成已停止或已回滚       |
| 设备离线     | 等当前任务结束，退出 Bridge，再委托新工作          | 显示不可执行或等待原因，不给虚构完成报告      | 下一步是否清楚                     |
| 结果可复用   | 完成一项工作后提出相同请求                         | 关联既有结果或说明需要复核的差异              | 是否省去重复劳动                   |
| 页面结构     | 交替点群成员与上下文/资料                          | 同时最多一个右侧栏，群聊导航持续高亮          | 是否影响持续聊天、手机能否操作     |

规则模式的精确重复要求范围、基线、验收、约束等一致。给同一目标换一种说法，属于下一轮真实模型测试；模型尚未配置时应记录为当前能力边界。

停止测试需要足够长的真实执行窗口；inspection 通常很快结束，不适合用来证明取消可靠性。正常已完成的任务也不应被当成“停止成功”案例。

### 连接只读执行设备

先准备一个至少有一次提交、用于试用的 Git 仓库。在试用网页中生成配对码，然后在另一个终端执行：

```powershell
Set-Location -LiteralPath 'E:\项目实践2\demo'
pnpm bridge -- --pair YOUR_PAIRING_CODE --api 'http://127.0.0.1:3003' --repo 'D:/your-pilot-repository' --runtime inspection --data-dir '.local/pilots/customer-01/bridge-inspection'
```

在网页选中该仓库，保存只读执行策略。inspection 会实际枚举仓库文件，但报告标识“未调用 AI”，只验证执行链可用。

要体验模型产出的价值，按 README 配置独立的 Pi 模型，在网页撤销并核清旧设备后，用新配对码和新 Bridge 数据目录连接 --runtime pi，先保持只读。协调器模型负责理解与比对，Pi 模型负责执行，只配好其中一个不会自动启用另一个。

当前不提供任意 Shell、新建/删除文件、运行测试或自动提交；所以第一批客户任务应选现有代码分析、风险梳理、接口说明检查等实际支持的目标。不能用“完整从零生成并运行一个新项目”作为当前版本已经支持的宣传。

## 5. 邀请其他电脑或手机体验前，先准备 HTTPS

先完成本机三角色闭环。多机试用不能只把 API_HOST 改为 0.0.0.0，再分享一个普通 HTTP 局域网 IP：当前前端在生成消息与请求 ID 时使用 crypto.randomUUID，浏览器通常只在安全上下文中提供该方法。localhost 的本机例外不能套用到其他设备访问的局域网 IP。[浏览器能力要求](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)。

可执行的下一阶段步骤：

1. 按 [部署手册](../runbooks/deployment.md) 配置测试域名、HTTPS 反向代理、独立 PostgreSQL、独立数据目录和试用账号。
2. 使用已有 infra/compose 模板构建测试实例；需要运行中的 Docker、已正确解析的域名和模板要求的环境变量：

```powershell
docker compose -f infra/compose/compose.yaml --env-file infra/compose/.env up --build -d
```

3. 所有成员使用同一个 https://测试域名，WEB_ORIGIN 必须与之完全一致。Bridge 在主设备上配对该 API 地址，连接改为 WSS。
4. 在真实电脑和手机分别验证登录、加入群、发送消息、资料引用、SSE 更新和 Bridge 回传，再发出试用邀请。
5. 客户只获得自己的账号与浏览器入口；模型凭据继续保留在主设备服务和 Bridge 环境。

该部署模板和多机 HTTPS 路径尚未在本环境验收，属于扩大试用前的待完成工作。若当前只想观察客户使用界面，可以先安排同机的受控体验，不必等待公网部署。

生产模式已强制 HTTPS WEB_ORIGIN、PostgreSQL 和绝对持久目录。Cookie 的 Secure 属性和 WebSocket 的 TLS/来源检查也需随真实入口核查。[Cookie 说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)、[WebSocket 部署要求](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)。

## 6. 第二轮：3～5 人，连续使用一周

选一个确实需要多人推进、已有少量代码的课程或个人团队项目。主设备维护者算在 MVP 的最多 10 个有效成员内。单执行设备并发仍为 1，不让多人同时争抢写入。

| 时间       | 任务                                           | 留下什么证据                                |
| ---------- | ---------------------------------------------- | ------------------------------------------- |
| 第 1 天    | 各成员独立完成首次使用与基础协作               | 操作耗时、卡住位置、需要帮助次数            |
| 第 2～3 天 | 用真实讨论登记人工工作，委托只读 Agent         | 每条候选/判断对应的消息、是否重复、是否有用 |
| 第 4 天    | 专门补测同义重复、范围变化、资料改版和误判纠正 | 人工期望与实际判断对照                      |
| 第 5 天    | 设备离线、停止、重登、刷新和手机输入           | 故障前后状态、恢复步骤、是否重复执行        |
| 第 6～7 天 | 连续自然使用，不布置强制 AI 次数               | 自发委托、复用结果、重复劳动和打扰情况      |

真实工作记录与故意构造的边界案例分别统计。不要为了提高数据而强行制造大量重复请求，或把用户自己放弃重做归功于系统拦截。

可以让同一个团队分两段完成规模相近的任务：一段按平常聊天协作，一段使用本产品，并记录重复开工与协调用时。先后顺序及熟悉程度会影响结果，小样本只能作为方向性证据。

### 真实模型的最低评测集

试用前由两人独立标注一批请求，冻结标签后再看系统输出。建议先做：

- 20 条确实重复：包含同义表达、人工进行中、Agent 进行中、已完成。
- 30 条相似但不同：客户端、版本、基线、验收或约束有明确差异。
- 10 条缺少信息：理应澄清，不能直接执行或武断拒绝。
- 10 条普通聊天或 @成员：不应启动执行。

记录重复拦截的查准率、召回率，以及不确定/澄清的比例。澄清不能直接算成拦截成功；同时报告原始分子/分母与未决样本，避免小样本百分比掩盖问题。

## 7. 记录表与是否继续推进

每个问题统一记录以下字段，可先存入 .local/pilots/customer-01/feedback.md；用户原话和群消息可能包含隐私，分享前做脱敏：

| 案例 | 客户目标与原话      | 预期行为       | 实际行为   | 可核查依据                 | 严重程度       | 后续动作   |
| ---- | ------------------- | -------------- | ---------- | -------------------------- | -------------- | ---------- |
| U01  | 想把已有工作交给 AI | 关联已有负责人 | 待体验填写 | 群/消息/目标/尝试 ID、截图 | 阻断/较重/轻微 | 修复或复测 |

优先看五件事：

1. 上手：5 个观察对象中，至少 4 个无需口头提示完成加入群、发消息、认领和委托。
2. 判断：20 个标注的确实重复案例，建议至少 18 个被正确关联或拦截；30 个明确不同案例中不接受未经解释的误拦截。分别报计数，未决案例单列。
3. 可纠正：所有参与者都能找到原因与复核入口，纠正时不必重新建群或重写整条需求。
4. 可信度：出现越权、虚构成功、重复执行或把未确认停止显示为已停止时，优先修复再扩大试用。
5. 产品价值：一周内是否有人自发再次使用；至少收集 3 个可核实的“避免重复开工 / 复用成果 / 缩短协调”的例子，同时记录打扰和误判成本。

消息到协作卡的等待时间、排队时长、执行耗时、停止请求反馈和确认耗时分别记录，不能混成“AI 响应时间”。样本少时展示原始耗时，不宣称稳定 P95。规则与真实模型、inspection 与真实 Pi 结果分别汇总。

结束访谈只问具体经历：

- 最近一次不知道 Agent 在做什么发生在哪里？
- 哪一次判断让你不信任它，你最后怎样处理？
- 如果下周没有这个产品，哪件事情会重新变麻烦？

先修复阻断使用与损害信任的问题，再决定是否扩展高级能力。使用流畅但没有真实节省，也说明核心价值仍需要调整。
